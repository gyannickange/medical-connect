# Project instructions for Claude Code

## Git

- Never run `git commit` or `git push` without the user's explicit go-ahead, every time. Do not treat a prior approval as standing permission for later commits in the same session.
- When executing a multi-task implementation plan (e.g. via subagent-driven-development), skip the per-task "commit" steps. Implement and test all tasks with changes left uncommitted, then ask the user once at the end whether/how to commit.
- Design specs under `docs/superpowers/specs/*` are written to disk only — never `git add`/`git commit`/`git push` them, even when a skill's own instructions say to commit. This overrides those skill instructions.

## Frontend (React) — read before writing any JSX

- **Never write raw HTML elements when an equivalent component already exists in `frontend/src/components/ui/`.** Before writing `<button>`, `<input>`, `<div>` styled as a card/alert/banner, `<select>`, `<dialog>`, `<textarea>`, a checkbox/switch/radio, a tooltip, a tabs UI, etc. — check `frontend/src/components/ui/` first (list it: `ls frontend/src/components/ui/`). If a matching component exists (`Button`, `Input`, `Alert`/`AlertDescription`, `Dialog`, `AlertDialog`, `Select`, `Textarea`, `Checkbox`, `Switch`, `Tabs`, `Card`, `Badge`, `Tooltip`, etc.), use it — never hand-roll the equivalent with raw tags and Tailwind classes, even for something that looks trivial (e.g. an inline "Retry" text-button should be `<Button variant="link" size="sm" className="h-auto p-0">`, not `<button className="underline">`). This applies to every session and every subagent this project's Claude Code touches — it has been missed before and had to be fixed after the fact; check the `ui/` folder every time, don't assume "this one's too simple to need it."
- This project is **Vite + React + TypeScript + Wouter** (client-side routing), **not Next.js**. There is no App Router, no `next/image`, no `next/link`, no server components, no `getServerSideProps` — don't apply Next.js-specific patterns here, they don't exist in this stack.
- Follow the codebase's existing conventions rather than inventing new ones:
  - i18n: all user-facing strings go through `t("key")` from `frontend/src/lib/i18n.ts`, added to **both** `en` and `fr` dictionaries — never hardcode a string. `frontend/src/lib/i18nCompleteness.test.ts` enforces this.
  - State/data access: reuse existing contexts/hooks (`useAuth`, `useTenant`, `useToast`, `useTranslation`, `useQuery`/`useMutation` via `@tanstack/react-query`) instead of introducing parallel state.
  - Testing: this project has no `@testing-library/react`/jsdom setup (vitest runs with `environment: "node"`). Business logic belongs in plain, fully-unit-tested `lib/`/`hooks/` functions; thin React components/hooks that just glue tested logic together are left untested, matching existing files like `useNativeLANAgent.ts`/`GlobalNativeLANAgent.tsx`. Don't add new test infrastructure (jsdom, RTL) without asking first.
  - Styling: Tailwind utility classes via the existing `cn()` helper (`frontend/src/lib/utils.ts`), no inline `style={{}}` unless truly dynamic/computed.
  - Naming: match existing `data-testid` conventions (kebab-case, `button-*`/`input-*`/`*-modal` style) when adding new interactive elements.
- Small, focused files over large ones; one clear responsibility per module. Don't restructure files you're not otherwise touching.

## Backend (NestJS) & database — read before touching `backend/`

- **This project uses a CouchDB/PouchDB local-first architecture** (each desktop "caisse" gets its own local, offline-capable replica, syncing peer-to-peer over LAN and optionally through a central server). See `docs/superpowers/specs/2026-08-09-lan-peer-sync-design.md` for the target architecture and inspect the current repositories/services for the implemented state. **Do not introduce PostgreSQL, SQLite, or another database technology without asking the user first.**
- **The REST API is a durable contract across independently-installed desktop builds — treat every existing endpoint/DTO as frozen.** This project ships as a compiled Tauri desktop app; different "caisses" on the same LAN or talking to the same central server can be running different, independently-updated versions indefinitely (nobody force-updates them all at once). Concretely:
  - Never change the meaning, type, or required-ness of an existing field on an existing DTO/response, never remove a field a shipped client may read, never change an existing route's URL, method, or status codes in a breaking way.
  - Adding a new **optional** field to a request/response DTO is fine (older clients simply won't send/read it — this is how `deviceId?` was added to `UpdateProductDto` for the edit-lock feature: optional, ignored by any client that doesn't know about it).
  - If a change is genuinely breaking (removing/renaming a field, changing semantics, changing a route's behavior in an incompatible way), it must ship as a **new versioned route** (e.g. `/api/v2/...`) alongside the old one, kept working, not a replacement of it. Don't silently break old clients — ask the user before making any change that isn't purely additive to a shipped endpoint.
- **Multi-tenancy is enforced by role only, not by resource ownership — be careful here.** `*.policy.ts` files (`backend/src/modules/*/*.policy.ts`, extending `BasePolicy`) only check the caller's role (`isAdmin()`/`isAdminOrManager()`/etc.), and most storage-layer lookups (`backend/src/lib/database-storage.ts`, e.g. `getProduct(id)`) fetch by primary key alone with no `tenantId` filter. This is a pre-existing, systemic pattern across the codebase, not something introduced by any single feature — but it means an admin/manager of tenant A can currently reach a resource belonging to tenant B if they know/guess its id. When adding a new endpoint or service method that takes a resource id: prefer deriving the tenant scope from the already-authenticated resource (fetch it, then compare `resource.tenantId` to `req.user.tenantId`) rather than trusting a client-supplied `tenantId`, and flag to the user if you notice a write path that's missing this check — don't silently "fix" the whole system unprompted, but don't add new unscoped lookups either.
- **Database: Drizzle ORM + PostgreSQL.** Schema lives in `backend/src/shared/schema.ts` (`pgTable(...)`), migrations are generated via `drizzle-kit` into `backend/drizzle/` (config: `backend/drizzle.config.ts`). The pooled connection is `pool`/`db` from `backend/src/lib/db.ts` (a plain `pg.Pool`, default sizing — no explicit min/max tuning currently).
  - **Most `tenantId` columns have no index.** Only two `index`/`uniqueIndex` definitions exist in the whole schema today (a normalized-username uniqueness constraint and a per-tenant barcode uniqueness constraint) — every `getXByTenant(tenantId)` style query (there are ~30+ `tenantId`-filtered queries across the storage layer) is an unindexed filter. If you're adding a new frequently-queried `tenantId`-scoped table/column, add an index (`index("table_tenant_idx").on(table.tenantId)`) as part of that change; don't leave a new one unindexed just because the existing ones are.
  - **No multi-step write in this codebase currently uses `db.transaction(...)`.** If you add a new operation that writes to more than one table and both writes must succeed or fail together (e.g. a sale + stock deduction), wrap it in a transaction — don't assume "the existing code doesn't do this" is a reason to skip it for something that actually needs atomicity.
  - Prefer Drizzle's typed query builder (`db.select().from(table).where(eq(...))`) over raw SQL; reuse `and()`/`eq()` composition already used throughout `database-storage.ts` rather than inventing a new query style.
- **Current transitional write pattern for already-migrated entities (see the migration-status note above — don't assume this is the end state):** for products (and any other entity confirmed migrated in the latest plan docs), CouchDB is mirrored as best-effort via **optional** constructor params (`private readonly xService?: XService`) called with `void this.xService?.method(...)` (fire-and-forget, errors swallowed) — today, the PostgreSQL write still succeeds/fails independently of CouchDB being reachable for these entities. The one exception is a check that's actually a required guard rather than a side-effect mirror (e.g. `productsLockService?.assertHeldByDevice(...)` in `ProductsService.update()`): that one IS `await`ed and allowed to throw, because it enforces a real business rule (who holds the edit lock), not data mirroring — that distinction (best-effort mirror vs. required guard) stays relevant regardless of which database ends up primary. When touching an entity not yet mentioned in the migration plans, don't assume either direction — ask.
- **Auth/authorization pattern to reuse, not reinvent:** `@UseGuards(JwtAuthGuard, PolicyGuard)` on the controller + `@CheckPolicy(SomePolicy, "action")` on each route, backed by a `SomePolicy extends BasePolicy` class. Add new permission rules there, not as ad-hoc `if` checks inside controller/service methods.
- **Validation:** every request body goes through a `class-validator` DTO (`@IsString()`, `@IsOptional()`, `@IsNotEmpty()`, `@IsNumber()` + `@Type(() => Number)` for numeric coercion from query/body). Never accept an untyped/unvalidated body — add a DTO field, don't reach into a raw request object.
- **Testing:** backend service specs (`*.service.spec.ts`) construct the service directly with plain Jest-mocked dependencies (`new SomeService(mockedDep as any)`), not NestJS's `TestingModule` — match this lighter-weight pattern for new service tests unless there's a specific reason a full DI container is needed.
